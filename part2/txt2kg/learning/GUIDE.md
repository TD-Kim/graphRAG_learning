# txt2kg 읽기 가이드

원본 [`txt2kg.py`](../txt2kg.py)(430줄)를 옆에 열고 이 순서대로 읽으세요.

## 한눈에 보기

```
위키 텍스트 ─▶ ① 청킹 ─▶ ② LLM 추출(청크마다) ─▶ 병합·중복 제거 ─▶ ③ 검증 ─▶ JSON 저장 ─▶ ④ Neo4j 저장
              500자/겹침100   엔티티 + 관계 JSON    이름 기준             끊어진 관계 제거          MERGE 노드, CREATE 관계
```

csv2kg 와 가장 큰 차이: **스키마(레이블, 관계 타입)를 사람이 정하지 않고 LLM 이 정한다.**
그래서 "LLM 이 뽑은 것을 얼마나 믿고, 어떻게 정리해서 넣을까"가 이 실습의 핵심이다.

## 함수별 "왜"

### `split_text_into_chunks`
- **왜 자르나**: 한 번에 너무 많은 글을 주면 LLM 이 엔티티를 빠뜨리거나 뭉뚱그린다. 짧게 주면 꼼꼼해진다.
- **왜 겹치나(`chunk_overlap=100`)**: 문장이 청크 경계에서 잘리면 주어와 목적어가 다른 청크로 갈라져 관계를 못 뽑는다. 앞뒤를 겹쳐 그걸 줄인다.
- **`separators` 순서**: 문단(`\n\n`) → 줄 → 문장(`. `) → 단어 순으로 "가능한 큰 단위"에서 먼저 자른다. 문장 중간을 자르는 일을 최소화한다.

### `extract_knowledge_from_chunk` (가장 중요)
- 시스템 프롬프트는 4개 블록으로 되어 있다. 각 블록이 무엇을 막으려는지 생각하며 읽자.
  - `<extraction_strategy>`: 동사를 먼저 찾고 주어/목적어를 정하는 "관계 우선" 전략. 엔티티만 먼저 뽑으면 관계가 빈약해진다.
  - `<rules>`: 피동형 "A는 B에 의해 ~된다" → `(B)->(A)` 처럼 **방향** 규칙이 핵심. 한국어 피동문에서 LLM 이 방향을 자주 뒤집는다.
  - `<examples>`: 규칙만으로는 모호한 경우를 예시로 고정(few-shot).
  - `<output_format>`: 파싱할 JSON 모양. `evidence`(원문 문장)를 받는 이유는 나중에 "왜 이 관계가 생겼는지" 추적하려고.
- `response_format={"type": "json_object"}`: JSON 이 아닌 응답이 오지 않게 강제. 그래도 **필드가 빠질 수는 있다** → 아래에서 `.get()` 으로 방어한다.
- `temperature=0`: 같은 입력에 같은 결과. 추출 작업은 창의성이 아니라 일관성이 중요하다.
- 실패하면 빈 결과를 돌려준다: 청크 하나 실패로 전체가 멈추지 않게.

### `extract_knowledge_batch`
- **엔티티 병합**: 같은 이름이 여러 청크에서 나오면 하나로 합치고 속성은 덮어쓰며 합친다(`{**old, **new}`).
- **관계 중복 제거**: `(source, target, type)` 이 같으면 하나만. `all(key)` 로 셋 중 하나라도 비면 버린다.
- 참고: 함수 기본값은 `gpt-4.1` 이지만 `main` 에서 `gpt-4o` 를 넘기므로 실제로는 `gpt-4o` 로 돈다.

### `validate_knowledge_graph`
- LLM 은 엔티티 목록에 없는 이름을 관계에 쓰기도 한다. 그대로 저장하면 아래 `MATCH` 가 실패해 관계가 조용히 사라지므로, 미리 걸러서 **몇 개가 버려졌는지 보이게** 한다.

### `save_to_neo4j`
- 레이블(`node_type`)과 관계 타입(`rel_type`)은 파라미터로 못 넘기므로 f-string 으로 넣고 백틱(`` ` ``)으로 감싼다. 한국어 레이블(`인물`)이나 공백도 백틱으로 감싸면 쓸 수 있다.
- 노드는 `MERGE`(있으면 재사용), 관계는 `CREATE`.
- f-string 안의 `{{ }}` 는 Cypher 의 중괄호를 쓰기 위한 이스케이프다.
- `execute_write(트랜잭션 함수, 인자)`: 노드 전체를 한 트랜잭션으로 쓴다. 중간에 실패하면 전부 롤백된다.

## 생각해 볼 점 (면접에서 물어볼 만한 것)

1. **MERGE 키에 속성까지 들어간다** (316줄): `MERGE (n:개념 {name: $name, year: $year})` 는 이름이 같아도 year 가 다르면 새 노드를 만든다. 보통은 `MERGE (n {name})` 후 `SET n += $props` 로 쓴다. 왜 그쪽이 나을까?
2. **관계의 MATCH 에 레이블이 없다** (341줄): `MATCH (source {name: $source})` 는 모든 노드를 훑는다. 이름이 같은 노드가 레이블별로 둘 있으면 관계가 두 개 생긴다.
3. **LLM 출력이 쿼리 구조에 들어간다**: 레이블/관계 타입/속성 키는 LLM 이 만든 문자열이다. 백틱만 제거하는 것으로 충분할까? 속성 키에 공백이나 `-` 가 있으면?
4. **같은 개념, 다른 이름**: "단백질"과 "단백질(protein)"은 다른 엔티티가 된다. 엔티티 정규화(entity resolution)를 어디서 할까?

## 실행 전 체크
- `.env`: `OPENAI_API_KEY`, `NEO4J_URI`, `NEO4J_USERNAME`, `NEO4J_PASSWORD`
- `save_to_neo4j` 는 **DB 전체를 지우고** 시작한다.
- 결과 JSON 은 `knowledge_graph.json` 으로 저장된다. Neo4j 없이 추출만 확인할 수도 있다.
